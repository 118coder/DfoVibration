## 一、问题 1: 国产手柄识别 (VID 20BC:5158)

### 现象
国产手柄(DirectInput/HID 档, VID=20BC, PID=5158)插入后软件无任何反应, XInput 通道也不识别。

### 诊断
- 软件同时监听 XInput 与 RawInput 两条通道:
  - XInput 通道身份恒为 045E:xxxx (微软虚拟身份), **无法与物理 VID:PID 直接比对**;
  - RawInput 通道能拿到真实 VID 20BC:5158, 但原 HID 过滤 `usage_page/usage` 匹配策略过严,
    且未对该厂商做针对性兼容。
- 手柄激活依赖"按下→松开"上报基线, 上报格式异常(小报文/低电平有效)会导致激活失败连锁。

### 修复(已部署并验证)
1. 放宽 HID 过滤: 同时支持 Generic Desktop (0x01) 与 **Game Controls (0x05)** 两页,
   覆盖国产手柄/方向盘/飞行摇杆等不同上报用法; 报文最小长度从偏严值放宽到 8 字节
   (部分国产手柄只有 8 字节报文)。
2. 兼容高/低电平有效按键布局与 8 字节小报文。
3. 双通道仲裁: 激活流程写 `Config.toml` 的 `[[hid_baselines]]`, 基线存哈希后的设备身份,
   重启自动识别。

### 验证
国产手柄 XInput 档与 HID 档均识别; 激活一次后即插即用。

## 二、问题 2: 激活流程失败

### 现象
非 XInput 模式手柄第一次插入弹出【设备激活】窗口, 按任意键仍无法完成, 反复弹窗。

### 诊断
- 基线建立依赖"按下事件 + 松开事件"成对上报; 部分国产手柄按下期间只上报一次、
  或以状态帧方式上报(无独立 KeyUp), 导致基线采集超时/不完整。
- 激活状态机在异常上报序列下重置, 形成死循环。

### 修复
- 激活采集改为"收到任意有效帧即建立基线", 不再强依赖独立 KeyUp;
- 对重复上报/中途拔插做幂等处理, 激活失败给出明确提示而非静默重试;
- 激活成功后立即写盘, 后续启动直接命中基线不再弹窗。

## 三、问题 3: 概率性夺取键盘鼠标 + 应急保险键

### 现象
高强度连发时, 切换窗口/切到桌面后, 键盘鼠标仍被注入"劫持", 系统几乎无法操作;
偶发映射失控, 界面卡死无法退出。

### 诊断(结论: 用户怀疑白名单问题, 诊断确认方向正确)
- 注入链对所有前台进程一律生效(未按进程过滤);
- 连发重复路径按完整"按下→等待→松开"周期逐条排队执行, 风暴时堆积;
- 无全局应急出口, 软件卡死时只能拔手柄/强制杀进程。

### 修复(v1.5 保险轮, 已部署验证)
1. **应急保险键**: `Ctrl+Alt+Shift+A` 全局强制退出 —— 由 Windows 直接识别该热键,
   即使软件自身已失控也能生效(注册失败时静默跳过)。
2. **注入保险**: 滑动窗口限流, 每秒注入超过上限(900 单元)自动进入 1 秒冷却;
   冷却期间整体"透传"(不拦截、不注入), 按键永远直接有效, 不会出现"注入被停按键被吞"。
3. **进程白名单**: 空=全部启用(默认); 填入 DNF exe 名后, 只有 DNF 前台时注入生效,
   切回桌面/其它程序自动停止注入 —— 消除"切到桌面还被抢鼠标"。
4. 应急键 + 白名单逻辑加入使用说明【应急保险(重要)】章节。

## 四、问题 4: 中文拼音输入法与软件冲突

### 现象
打开拼音输入法打字(组合选字)时, 聊天输入卡死、字母被手柄映射"打"进聊天框。

### 诊断
- 钩子回调对按键做拦截式注入, 输入法组合期间收不到 KeyUp → 输入法状态卡死;
- 手柄按下触发映射注入, 注入的字母键被输入法当作真实打字输入。

### 修复(v1.5 输入法轮, 已部署验证)
1. 新增 IME 组合检测(`ImmGetContext + ImmGetCompositionStringW(GCS_COMPSTR)`):
   正在打字(组合选字)期间, **整个映射与注入链自动暂停** —— 不拦截按键(输入法收得到 KeyUp)、
   不注入模拟键(字母不会打进聊天框)。
2. 打完字按 Esc / 选字完成即自动恢复, 无需任何操作。
3. 仅"正在打字"时暂停; DNF 开着拼音但没打字时不暂停, 不影响打副本。
4. v1.6 将 IME 检测改为 **10ms 节流缓存**(见问题 7), 热路径不再每事件调 Imm API。

## 五、问题 5: 第三方无线接收器 + 蓝牙双连接冲突

### 现象
同一型号手柄同时连着"第三方无线 USB 接收器"与"蓝牙", 两路同时上报 → 按键加倍/冲突。

### 诊断
同一物理手柄被系统识别为两台设备(RawInput 两路), 两路都映射注入 → 一个键按出两次。

### 修复(v1.5 双连接轮, 已部署验证)
- 默认由 **XInput(接收器)接管**: 蓝牙那一路的 HID 接口被跳过,
  避免两路同时注入产生加倍/冲突。
- 若需使用蓝牙那一路: 拔掉接收器, 或把接收器侧切换为非 XInput 模式。
- 已写入使用说明【应急保险】第 6 条。

## 六、问题 6: 狂按某键 + 来回切换键位打连招时卡死

### 现象
用户澄清: 不是"单键连按", 而是**连招期间高频来回切换键位** → 概率性卡住/崩溃。

### 诊断(两轮分析)
- worker 对每个"按下"都执行完整注入周期(按下→sleep(duration)→松开), 串行执行;
- 事件走无界 mpsc 队列, 处理跟不上时无限积压; 积压期间连续注入让系统输入被淹没;
- 释放后积压仍被逐条重放 → "松手后还在狂按"的卡死感;
- 冷却期旧实现"拦截但不注入" → 按键被吞, 进一步加剧卡死感。

### 修复
#### v1.5 第一轮(连招节拍化 + 冷却透传)
1. **连发(涡轮)节拍化**: 连发键按下的处理改为"只登记状态", 统一由定时器按 interval 节拍注入;
   高速连按/来回切键不再叠加完整注入周期 → 积压源头被切断; 物理松开即停。
2. **冷却期整体透传**: 冷却期内不拦截也不注入, 按键永远直接有效(如上)。

#### v1.6 第二轮(背压合并, 本轮核心之一)
3. **事件背压自动合并**: 全局原子积压计数(`EVENT_BACKLOG`, dispatch +1 / worker -1),
   积压 ≥512 触发 `drain_and_coalesce` —— 快速清空队列, 丢弃中间冗余事件,
   只保留每个设备最新的"按下/松开"状态后合并处理:
   - **松开必然保留** → 松手立即停止, 绝无"无界积压 → 松手后狂按";
   - 移动/滚动事件在背压期间限流丢弃, 不积压。
4. `input_timeout` 读值钳位 `[1, 2000]ms`(构造/重载/读取三处):
   配置填 0 或超大不再让 worker 空转烧 CPU 或长时间卡住。
5. 双击间隔 `double_tap_gap_ms` 钳位 `[1, 500]ms`, 防大值阻塞 worker。

## 七、问题 7(本轮主线): 概率性"程序卡住然后崩溃"

### 现象
高强度使用(连招/连打/长时挂机)时, 程序偶发卡住随后整体崩溃退出, 无任何提示。
用户要求: **优化结构, 保证绝对稳定**, 允许多子代理协同分析。

### 诊断(双子代理独立审查 + 交叉验证, 结论一致)
崩溃前 5 大根因:
1. **`panic = "abort"`**: 任意线程 panic 直接杀整个进程 —— 一崩全崩(最致命);
2. **事件积压**: 无界 mpsc + worker 串行 sleep(duration), 非 turbo 重复路径仍逐周期 sleep;
3. **无输入钳位**: `input_timeout` 未 clamp, 异常配置可让 worker 长期不取事件或空转;
4. **白名单热路径锁争用 + 锁内调 WinAPI**: `process_whitelist` 持锁调
   `OpenProcess/QueryFullProcessImageNameW`, 锁内慢操作放大争用;
5. **不可信输入未校验**(子代理 B 补充):
   - `rawinput.rs` 用 `dwSizeHid×dwCount` 直接建切片(上限 ~4.29e9), 越界读 → 崩溃头号嫌疑;
   - baseline 短于 `SKIP_BYTES` 时切片 panic, 且发生在 `window_proc` (extern "system" FFI 回调)内
     —— panic 穿越 Win32 帧 unwind 属未定义行为, 几乎必崩;
   - 振动 DLL 共享内存环形缓冲 `capacity` 可被污染: `t % 0` 除零 / 越界读 / 头尾异常死循环。

### 修复(v1.6 绝对稳定化, 四大支柱 + 专项加固)

#### 支柱 1: 崩溃不再致命
- `Cargo.toml [profile.release]`: `panic = "abort"` → `panic = "unwind"`;
- 全局 panic hook(`setup_panic_hook`): 任何 panic 先写日志再 unwind, 进程不退出;
- 崩溃日志落地: `SorahkDFO_crash.log`(与 exe 同目录, `crash_log_path()`)。

#### 支柱 2: 线程级监督(有错自动重启, 进程永不死)
- `util::spawn_supervised`: 线程闭包包 `catch_unwind`, panic 后 300ms 自动重启,
  最多 10 次后放弃但进程保持存活; 正常返回不重启;
- 键盘钩子 / 鼠标钩子 / 托盘三线程全部改为受监督启动;
- 所有 `thread::spawn(...).expect(...)` 降级为"记日志 + 跳过/占位", 不再 panic(键盘 worker×2、
  RawInput 线程等);
- `FnMut` 监督闭包捕获值改为 `.clone()` 使用, 支持多次重启消费。

#### 支柱 3: 锁防中毒
- `util::lock_guard / read_guard / write_guard`(PoisonError → `into_inner` 降级);
- state.rs 全部 7 处 `Mutex/RwLock .unwrap()` 替换为防中毒获取;
- `is_process_whitelisted` 重构: 锁内**只 clone 白名单**(轻量), 释放锁后再查前台进程
  (WinAPI 不再持锁调用), 消除热路径锁内慢操作。

#### 支柱 4: 背压与钳位(见问题 6)
- 背压合并 `drain_and_coalesce` + `input_timeout [1,2000]` + 双击间隔 `[1,500]`;
- IME 检测 10ms 节流缓存(`is_ime_composing` 改为静态缓存, 热路径不再每事件调 Imm API)。

#### 专项加固(子代理 B 高危清单逐项落实)
| 位置 | 问题 | 修复 |
|------|------|------|
| rawinput.rs | `from_raw_parts` 无上限校验 → OOB 读 | 与真实缓冲容量比对(传 `buffer.len()`, 减 bRawData 偏移), 超界丢弃该帧 |
| rawinput.rs | baseline 短切片 panic + FFI 回调内 panic=UB | `count_changed_bits` 长度守卫; `window_proc` 整体包 `catch_unwind`, panic 兜底返回默认窗口处理 |
| vibration.rs | 共享内存环形缓冲 `capacity=0` 除零 / 越界 / 死循环 | `capacity` 校验(≥事件大小、≤VIB_RING_SIZE、整除事件大小)、head/tail 范围校验、单轮迭代上限 `max_events`; 异常丢弃本轮并写日志 |
| keyboard.rs | `std::mem::discriminant` 读底层表示(UB) | 显式序数映射 `Gamepad=1 / Joystick=2 / HidDevice=3` 再哈希 |
| input_manager.rs | XInput 轮询线程 `loop{}` 无终止 | 循环加 `while !xinput_state.should_exit()` |
| keyboard.rs 监控线程 | 退出链"join 全部 worker 后才发 WM_QUIT" → 退出卡死 | `should_exit` 门控 + 等 worker 最多 3 秒, 超时直接 `PostThreadMessageA(WM_QUIT)` |

#### 自检发现并修复的缺陷
- 首版监控线程实现为"启动后 3 秒即发 WM_QUIT"(worker 正常运行本来就不该退) →
  会把钩子线程提前终止、映射静默失效。**改为先等 `should_exit` 再投递 WM_QUIT**,
  修复后自检 8 秒无异常、无误触发日志。

### 验证
- 编译: `cargo build --release` 零错误(exit 0);
- 启动自检: 启动 8 秒确认存活、无崩溃日志、无 SHUTDOWN_TIMEOUT 误触发;
- 高强度实测(用户): **连续高强度使用后未再出现卡死/崩溃**。

## 七·补、问题 8: 手柄组合键(如 Y+LT)被单键(如 LT)覆盖而失效

### 现象(用户实测)
映射设置中把手柄【LT】映射为键盘【A】、组合【Y + LT】映射为键盘【Q】后:
单独按 LT → 正常触发 A; 按 Y + LT → **依然只触发 A, 不触发 Q**(组合键实际失效)。

### 诊断
- XInput 通道的组合匹配(`handle_normal_mode_xinput`)对"当前激活输入集"匹配出**所有**命中组合
  (2 键组合 [Y,LT] 与 1 键组合 [LT] 同时命中), 然后**逐个全部派发** Pressed 事件;
- 于是按 Y+LT 时 **Pressed([Y,LT]) 与 Pressed([LT]) 同时注入** → Q 与 A 都在触发,
  且 A(单键, 先按住)持续注入 → 用户感知为"只触发 A、组合键失效"。
- RawInput 通道(`detect_hid_changes`)是"整组互斥": 激活集合整体哈希成一个 combo_id,
  天然只有大组合命中 → 无此缺陷; 唯独 XInput 通道缺"组合独占单键"的仲裁。

### 修复(组合独占优先级)
在 `xinput.rs` 派发前对命中组合做**子集剥离**:
- 若某命中组合 A 的按键集合被另一个更大的命中组合 B 完全包含(B ⊇ A), 则 A 被覆盖、不派发;
- 例: [Y,LT] ⊇ [LT] → 按 Y+LT 时仅派发 [Y,LT](→Q); 松开 Y 后 [LT] 恢复命中 → 自动切回 A;
- 复杂度 O(n²), n = 命中组合数(≤5), 仅在输入变化时执行, 无热路径影响。

### 验证
- 编译通过; 映射场景 [LT]→A + [Y,LT]→Q 手测: 单按 LT→A、Y+LT→Q、松开 Y→回 A, 切换正确。

## 七·补二、问题 9: 手柄报文长度漂移 → copy_from_slice panic + 高位按键检测盲区

### 现象(来自运行日志 SorahkDFO_crash.log 的直接证据)
用户在 v1.6 高强度使用后, crash.log 记录了 **199 对 PANIC + FFI_WINDOW_PROC_PANIC**,
全部来自 `rawinput.rs:1658`:
```
copy_from_slice: source slice length (45/60/30) does not match destination slice length (15)
```
进程未崩(FFI 兜底生效), 但**每一帧输入都被丢弃**, 并且检测区间被限制在
基线 15 字节内 → 落在 15 字节之后的按键/组合键**永远检测不到**(这是组合键失效的
另一个真实来源: 单独按 LT 在前 15 字节内可触发, Y+LT 中 Y 的高位字节被盲区吞掉)。

### 诊断
- 激活时采集的基线样本 15 字节, 而运行报文 30~60 字节(国产手柄报文长度随
  状态/报告模式变化, 或激活样本取自截断帧);
- 检测用 `min(current, last, baseline)` 做公共前缀比较, 不越界, 但:
  1. `state.last_data.copy_from_slice(current_data)` 长度不一致 → panic(每帧);
  2. 公共前缀之外的按键位被永久盲区覆盖 → 组合键/高位键失效。

### 修复(三处, rawinput.rs)
1. **reset 路径自适应拷贝**(665): 长度一致走 copy_from_slice, 不一致则重建 last_data;
2. **检测路径自适应拷贝**(1658): 同样按长度对齐后更新 last_data, 不再 panic;

## 七·补三、问题 10: 玩一会后战斗事件中断(震动消失), 映射正常 —— 振动环形缓冲校验误判

### 现象(用户实测)
v1.6 玩了一会后, 游戏战斗事件接收中断 → 震动效果突然消失;
但按键映射功能一切正常。1.5 版本无此问题。用户判断: 是 v1.6 改动引入。

### 诊断(根因: v1.6 上一轮加的环形缓冲校验语义写错)
- 共享环形缓冲 `VibRing` 中 **head/tail 是"累计字节偏移"**(DLL 每写一事件 head+=16、
  软件每读一事件 tail+=16, 二者持续增长、会超过 capacity=\`VIB_RING_SIZE\`=262144),
  通过 \`% capacity\` 取环内位置(见 DLL 端 dfovib.c: \`pos = head % r->capacity\`);
- v1.6 上轮加固时把校验写成 \`head <= capacity && tail <= capacity\` —— 这是把累计值
  误当"环内索引"。**玩一会后 head 累计超过 262144 → 该条件恒为 false → ring_ok 恒假
  → 每轮事件都被丢弃 → 震动中断**。开局时 head 尚小所以前几分钟正常, 之后才消失。
- 映射不受影响(走 RawInput/XInput 通道, 与振动共享内存无关), 与用户观察完全一致。

### 修复(差值语义 + 异常自愈, vibration.rs)
1. **合法判定改为头尾(无符号)差值**:
   \`let ring_ok = capacity == VIB_RING_SIZE \n    && capacity % ev_size == 0\n    && head.wrapping_sub(tail) <= capacity;\`
   未满(< capacity)与恰好满(= capacity)均合法; 差值过大(漏读落后/DLL 重启 head 回绕)才判异常。
2. **异常自愈**: 不再"一直丢" —— 异常时把 tail 同步到 head(丢弃积压旧事件),
   记日志 \`VIB_RING_INVALID(已同步 tail=head)\`, 下轮立即恢复读取, 不造成持续中断。
3. capacity 仍要求 == VIB_RING_SIZE(防除零/垃圾值/越界)。

### 验证
- 编译零错误; 长时间游玩战斗事件不再中断(以用户实测为准);
- 异常情形(DLL 重启/漏读)时只短暂丢弃积压后自动恢复, 不再持续中断。

## 九、已知边界与后续建议

1. **GUI 线程磁盘写**(main_window → config.rs 全量写 Config.toml): 杀软扫描/慢盘时可能卡 UI
   数秒; 建议后续将保存移入后台线程(当前 TryRecv 通道 + 注入限流兜底, 不阻塞主链)。
2. **钩子回调内的 1ms sleep**(release_modifiers_once): 连招触发时在回调内短睡,
   后续可移入 worker 线程执行。
3. **RawInput 消息循环**仍以 WM_CLOSE/WM_DESTROY 退出为主, message-only 窗口生命周期
   依赖进程退出(不强杀不阻塞); 如需完全优雅退出可仿 keyboard 监控线程补 WM_QUIT。
4. **SystemTime .unwrap()** 多处(理论不可失败): 可统一改 `saturating_duration_since`。
5. 若用户机器上出现 `SorahkDFO_crash.log`, 说明异常已被兜住(程序仍可继续用),
   把日志内容发回即可继续精修对应路径。
