# 音频→震动（飞智八爪鱼 6 Pro 式）模式技术调研

> 调研日期：2026-11-08
> 目标：为 DfoVibration（Rust + egui、Windows 单 exe、XInput 双马达）新增"实时采集游戏音频 → 智能识别场景/音效 → 生成震动反馈"模式，确定最优算法与开源依据。
> 约定：所有事实均附来源链接；无法核实的条目明确标注。本报告中的"我"指调研代理。

---

## 0. 结论速览（TL;DR）

1. **飞智"AI 音频震动"官方未公开算法细节**；可考证的链路是：常驻的 X-haptics 引擎实时读取音频（可仅限指定游戏进程）→ 频段分离/包络/瞬态处理 → 按左右声道与频带路由到 4 颗音圈马达。第三方分析认为其主体是**实时 DSP + 风格预设**而非神经网络；另有少量 UDP 遥测路线（如地平线系列）。详见 §2。
2. **学术界的最强参照**：POSTECH AuxLab（Yun & Choi）CHI 2023 / CHI 2025 的"游戏声音→实时触觉"管线（分类 + 语义映射），以及 CHI 2026 最佳论文 Sound2Hap（MIT 开源，但依赖 PyTorch/EnCodec，不适合本场景直接落地）。
3. **模型选型**：YAMNet（MobileNetV1、3.7M 参数、521 类、Apache-2.0）是唯一同时满足"够小、够准、许可证干净、有现成 ONNX"的 SED 模型；PANNs CNN14 / BEATs / AST 对 CPU 实时与分发都太重。
4. **Rust 生态齐备且活跃**：`wasapi`(0.27.0, MIT, 支持 loopback 与按应用录制) + `ort`(2.0.0-rc.15, MIT/Apache, ONNX Runtime 静态链接免 DLL) + `rustfft`(6.4.1)。**不需要 Python、不需要 libtorch、不需要附带 onnxruntime.dll**。
5. **许可证红线**：`aubio`（GPL-3.0）与 `essentia`（AGPL-3.0）**禁止**用于闭源单文件 exe；YAMNet 权重 Apache-2.0 干净；PANNs/EfficientAT 的 AudioSet 预训练权重存在"研究用途"灰区。
6. **推荐路线：A+B 混合**——纯 DSP（谱通量 onset + 频带能量）负责 ≤50ms 的枪声/爆炸瞬态响应，YAMNet-ONNX 语义层负责场景识别与 BGM/人声过滤，两者经规则映射表输出到 XInput 双马达。理由与风险详见 §6/§7。

## 2. 飞智（Flydigi）八爪鱼系列音频震动：公开资料

### 2.1 官方帮助文档（一手来源）

来源：[飞智帮助中心《AI算法加持下的音频触觉》](https://help.flydigi.com/docs/AI-suan-fa-jia-chi-xia-de-yin-pin-chu-jue%C2%A0)（已直接抓取核实，2026-11-08）

可考证的机制：

- **四种触发方式**：
  1. 官方适配游戏（列表内游戏直接开 X-haptics 总开关）；
  2. UDP 遥测游戏（"只支持地平线 4/5/6"，需在游戏里配 IP/端口）；
  3. **全局模式**："PC 上所有应用（含游戏在内）都有 AI 算法音频效果"；
  4. 自定义游戏（手动添加游戏 exe 路径）。
- **音频来源控制**：游戏适配模式"只读取游戏进程音频，不会受到外部音频干扰"；全局模式读取整机音频。
- **"纯净反馈"模式**："可以进一步过滤游戏中音乐和人声对话"——说明引擎内部存在音乐/人声的判别或过滤环节。
- **常驻引擎**：屏幕右下角"X-haptics 引擎需保持常驻"，即 Windows 端有一个本地常驻进程做音频处理（官方未说明云端/本地，但"常驻 + 即连即玩"强烈暗示本地实时处理）。
- **自定义**：可对扳机和握把分别设置震动风格。
- **官方未公开**：算法是否神经网络、模型架构、延迟指标——均未披露。

### 2.2 硬件与第三方技术分析

- [IT之家：飞智八爪鱼 6 系列发布，X-Haptics™ 四驱触觉反馈](https://www.ithome.com/1/003/525.htm)：Pro 版搭载 **4 颗宽频音圈马达（VCM）**，分置左右扳机与左右握把，四点独立驱动；工作原理接近微型扬声器。
- [GadgetHyper《X-Haptics Explained: How the Apex 6 Turns Audio Into Touch》](https://gadgethyper.com/blogs/news/flydigi-apex-6-x-haptics-explained)（第三方技术媒体，已直接抓取核实）给出的处理链（注意：**非官方文档，是其分析**）：
  1. 滤波清理 → 2. 频段分离（按"声学指纹"拆出枪声/爆炸/引擎/鼓点/贝斯）→ 3. 包络提取（起始/持续/衰减）→ 4. 瞬态增强 → 5. 频率合成 → 马达信号；
  - **空间路由规则**：尖锐瞬态（枪声/撞击）→ 扳机马达；环境能量（爆炸/路面/碰撞）→ 握把马达；左右声道 → 对应左右马达。
  - **两条路线**：路线 A 实时音频分析（默认，任何游戏/视频都生效，风格预设=不同的滤波阈值与频率权重）；路线 B 逐游戏遥测集成（读游戏数据，如地平线系列）。
  - 该分析明确说这是**实时信号处理**（"非 AI"），并指出已知缺点：背景音乐也会触发马达。
- [新浪财经报道](https://dj.sina.com.cn/article/niscekc4169327.shtml)：飞智空间站引入"AI 实时音频识别技术"，算法解析枪声/引擎声/环境音特征转触觉输出（宣传口径）。

### 2.4 小结：宣称 vs 可考证

| 问题 | 结论 |
|---|---|
| 是否本地分析 | 官方暗示本地（常驻引擎 + 仅读指定进程音频），未明说 |
| 是否神经网络"AI" | 官方宣传称"AI 算法"，第三方分析认为是**实时 DSP（频段+包络+瞬态）+ 风格预设**；无确凿证据证明有大模型 |

| 逆向资料 | 未找到公开资料 |

**对本项目的启示**：飞智的可考证路线（频带分离 + 包络 + 瞬态 + 声道路由 + 预设风格）与本文 §6 的路线 A 高度一致，证明该方案商业上成立；"纯净反馈"对应我们需要加一层音乐/人声门控（YAMNet 可补足这一点）。

### 3.2 传统信号处理线（标准算法出处）

- [librosa onset 模块文档](https://librosa.org/doc/0.11.0/onset.html)：onset 检测 = 计算谱通量 onset 强度包络（[onset_strength_multi](https://librosa.org/doc/0.11.0/generated/librosa.onset.onset_strength_multi.html)）+ 峰值拾取。
- [librosa Superflux 示例](https://librosa.org/doc/latest/auto_examples/plot_superflux.html)：复现 Böck & Widmer 2013 的 Superflux 算法（音标检测精度的经典基线）。
- [Dixon, "Onset Detection Revisited", DAFx 2006](https://www.dafx.de/paper-archive/2006/papers/p_133.pdf)：谱通量系 onset 检测的权威综述（常被引作标准算法出处）。
- [aubio 手册](https://aubio.org/manpages/latest/aubioonset.1.html)：onset 检测函数含 complex domain（用幅度+相位）、hfc 等；[aubio issue #106](https://github.com/aubio/aubio/issues/106) 指出默认 onset 用 **hfc**、tempo 用 **specflux**。
- [Essentia OnsetDetection 文档](https://essentia.upf.edu/reference/std_OnsetDetection.html)：多种检测函数（含 flux）的实现参考。

结论：onset 检测的"标准配方"就是 STFT → 谱通量（可加自适应阈值/峰值拾取），几十行 Rust + `rustfft` 即可实现，无许可证负担（librosa 的算法思想不受许可约束，实现要看代码出处）。

### 3.3 SED（声音事件检测）模型对比

| 模型 | 架构/参数 | AudioSet mAP | 输入格式 | 实时性 | 许可证 | ONNX |
|---|---|---|---|---|---|---|
| **YAMNet**（Google） | MobileNetV1 depthwise-separable，**3.7M 参数**，每 960ms 帧约 69.2M 乘加 | balanced mAP 0.306（官方 README） | **16kHz 单声道波形**，内部算 64 mel bin（125–7500Hz）、25ms/10ms STFT，0.96s 帧长 + 0.48s hop（来源：[tensorflow/models yamnet README](https://raw.githubusercontent.com/tensorflow/models/master/research/audioset/yamnet/README.md)，已直接抓取） | 极轻，CPU 远超实时 | **Apache 2.0**（[TF Hub 教程页](https://www.tensorflow.org/hub/tutorials/yamnet)） | 有现成导出：[audiomagic/yamnet-onnx](https://huggingface.co/audiomagic/yamnet-onnx/blob/main/README.md)（含 1024 维 embedding 输出）、[jafet21/yamnetonnx](https://huggingface.co/jafet21/yamnetonnx) |
| PANNs CNN14 | VGG-like 14 层 CNN，**~80M 参数**（checkpoint ~300MB） | 0.439 | 64 mel × ~1000 帧（音频重采样 32kHz） | CPU 实时吃力（80M 级 CNN） | 代码 MIT；**权重在 AudioSet 训练数据约束下为研究用途灰区**（[repo](https://github.com/qiuqiangkong/audioset_tagging_cnn)） | 无官方导出，社区有零散转换 |
| EfficientAT mn04 | MobileNetV3 蒸馏，**~4.4M 参数** | 0.471（mn04）；最优变体 0.483 | mel 谱 128 bin，32kHz 输入 | 小模型可边缘实时（[论文](https://arxiv.org/html/2211.04772v3)含推理时间对比） | 仓库 MIT（[repo](https://github.com/fschmid56/EfficientAT)）；权重同样受 AudioSet 灰区影响 | 无官方 ONNX（checkpoint 在 GitHub Releases，PyTorch 格式） |
| BEATs | 音频 tokenizer + masked prediction，**~90M 参数** | ~0.476（+AudioMAE 迭代） | mel 谱 | Transformer 推理重，CPU 不适合 | MIT 代码（[repo](https://github.com/microsoft/unilm/tree/master/beats)，[论文](https://arxiv.org/abs/2210.05775)） | 无官方 |
| AST | Audio Spectrogram Transformer，**~87M 参数** | ~0.445 | 128 mel | 全注意力，推理慢（[论文](https://arxiv.org/abs/2104.01778)） | 代码 MIT | 无官方 |

补充：YAMNet 类别是 **521**（AudioSet 原生 527 类中按公平性审查删掉 6 类，见上述 README）。参考实现：[SangwonSUH/realtime_YAMNET](https://github.com/SangwonSUH/realtime_YAMNET)（YAMNet+PyAudio 麦克风实时检测模板，Python）。

**YAMNet 延迟结构提示**：0.96s 帧长 + 0.48s hop → 语义事件天然有约 0.5–1s 的判断窗；适合做"场景层"（BGM/对话/环境），**不适合**做 ≤50ms 的瞬态触发——这正是需要 DSP onset 通道互补的原因。

## 6. 三条技术路线对比

> 前提约束：Rust 单 exe、Windows、端到端延迟目标 ≤50ms（指"音效发生 → 手柄开始震"）、不能强依赖 Python、闭源分发。

### 路线 A：纯 DSP（频带能量 + 谱通量 onset + 规则映射）

- **做法**：WASAPI loopback（`wasapi` crate，共享模式 ~10ms period）→ 分帧（如 1024 样本 @48kHz ≈ 21ms）→ `rustfft` → 低/中/高频带 RMS 能量 → 双马达强度（低频→左马达/主马达，高频→右马达/副马达）；谱通量（可加 hfc）+ 峰值拾取做 onset → 触发短脉冲包络；分频道能量 → 左右声道空间感。参考算法出处：[librosa onset](https://librosa.org/doc/0.11.0/onset.html)、[Dixon DAFx 2006](https://www.dafx.de/paper-archive/2006/papers/p_133.pdf)、[aubio hfc](https://aubio.org/manpages/latest/aubioonset.1.html)；映射算法可参考 [Sound2Hap 的 4 种 DSP 算法](https://github.com/Iris1215/Sound2Hap)（MIT）。
- **CPU 占用**：极低（FFT + 均值统计，远低于 1 个核的 5%）。
- **端到端延迟**：**可稳定做到 20–40ms**（10ms 采集 + 21–43ms 窗 + 计算 <1ms），满足 ≤50ms。
- **模型文件**：无；exe 体积零增加。
- **开发量**：中等偏小（约几百行 Rust + 调参 UI）。
- **上限**：**语义盲**——BGM 鼓点会被当成枪声；无法区分"受击"和"爆炸"；无法做"过滤音乐/人声"（除非再加节拍跟踪豁免）。这正是飞智"纯净反馈"要解决的问题。
- **风险**：逐游戏/逐风格调参工作量大；用户感知"震得热闹但不聪明"。
- **依据**：这正是 GadgetHyper 分析中飞智 X-Haptics 路线 A 的结构（§2.2）。

### 路线 B：轻量 SED 模型（YAMNet 级，ONNX + ort）

- **做法**：同一采集管线 → 重采样 16kHz mono → 0.96s 窗（stride 可取 0.24–0.48s）→ `ort` 跑 [yamnet-onnx](https://huggingface.co/audiomagic/yamnet-onnx/blob/main/README.md) → 521 类分数 → 规则映射表（如 `Gunshot/Gunfire,Explosion,Machine gun` 类目命中 → 对应强度/节奏包络）→ XInput。
- **CPU 占用**：YAMNet 每 0.96s 帧仅 69.2M 乘加（3.7M 参数，来源：[官方 README](https://raw.githubusercontent.com/tensorflow/models/master/research/audioset/yamnet/README.md)）；现代 CPU 上 ONNX Runtime 单线程跑约几毫秒/帧，整体 <1 核的 5–10%。
- **端到端延迟**：**语义事件固有 0.5–1s**（0.96s 窗 + hop）——**这是模型的性质，不是实现缺陷**；对"持续状态"（引擎声、环境声、BGM 门控）够用，对瞬态触发不够。
- **模型文件**：需要 yamnet.onnx（fp32 约 13–16MB；可用 fp16/int8 减半）。对"单 exe 分发"的影响：`include_bytes!` 内嵌（exe +约 15MB）或首次运行下载到 `%APPDATA%`；`ort` 的 ONNX Runtime 静态链接（§4.3），**不引入额外 DLL**。
- **许可证**：Apache 2.0，干净（§5）。
- **风险**：
  1. ONNX 图兼容性——有现成 HF 导出（audiomagic/yamnet-onnx）佐证可行，但需在 `ort` 2.0-rc 实测；
  2. AudioSet 521 类对"游戏音效"粒度有限（有 Gunshot/Gunfire、Explosion、Bark、Music、Speech 等，但没有"受击/技能吟唱"这类游戏语义），需要映射表 + 置信度阈值；
  3. BGM 场景下 Music 类持续高分——正好用作**门控信号**（抑制音乐触发枪声误判），即学术线"selective"思路（[CHI 2023](https://dl.acm.org/doi/10.1145/3544548.3580787)）。

### 路线 C：大模型/重方案（PANNs CNN14 / BEATs / 自训练）

- **CPU 占用**：CNN14 ~80M 参数（checkpoint ~300MB）；BEATs/AST ~90M 参数 Transformer——CPU 单帧推理数百 ms 级，实时化需 GPU 或强压缩；对本项目不可接受。
- **延迟**：即便压缩，语义窗 + 推理时间远超 50ms 目标。
- **模型文件**：300MB 级 → 单 exe 分发彻底破产（除非外置下载，体验差）。
- **许可证**：PANNs 权重研究用途灰区（§5）。
- **何时值得**：只有当未来要做"游戏专用自训练小分类器"（BattleSound WSED 思路：游戏音效数据集 + 小 CNN/LSTM，参考 [BattleSound](https://pmc.ncbi.nlm.nih.gov/articles/PMC9866824) 与 [CHI 2025 LSTM 方案](https://dl.acm.org/doi/10.1145/3713355)）时才进入；那是 V4 之后的事。
- **结论：不值得。**

### 对比表

| 维度 | A 纯 DSP | B YAMNet-ONNX | C 大模型 |
|---|---|---|---|
| CPU 占用 | <5% 单核 | 5–10% 单核 | 不可实时（CPU） |
| 端到端延迟 | **20–40ms** | 0.5–1s（语义窗固有） | >1s |
| 额外模型文件 | 无 | ~15MB（可内嵌） | ~300MB+ |
| 单 exe 兼容 | 完美 | 可（内嵌或首启下载；ORT 已静态链接） | 不兼容 |

| 语义能力 | 无（BGM 误触发） | 521 类场景感知 + 音乐/人声门控 | 最强但用不上 |
| 开发量 | 小–中 | 中（模型接线 + 映射表 UI） | 大 |
| 失败模式 | 调参繁琐、不聪明 | 瞬态延迟大、图兼容需实测 | 部署/许可双重失败 |

## 7. 推荐：A+B 混合（DSP 快通道 + YAMNet 语义层）

**架构**：

```
WASAPI loopback (wasapi crate, 10ms period, 48k→16k 重采样)
  ├─ 快通道 (DSP, 每帧): rustfft → 谱通量/hfc onset + 频带能量
  │     → 20–40ms 内触发瞬态震动包络 (枪声/爆炸起音, 双马达强度)
  └─ 慢通道 (语义, 每 0.24–0.48s): ort + yamnet.onnx → 521 类分数
        → 门控 (Music/Speech 高分时抑制快通道的 BGM 误触发; 对应飞智"纯净反馈")
        → 场景映射表 (Gunshot/Explosion/Engine... → 风格预设) + 用户自定义规则
  → 合成器 (冲突消解/优先级/强度上限) → XInput 双马达
```

**理由（引证）**：

1. ≤50ms 的硬指标只有 DSP 通道能满足（§6 路线 A），而飞智可考证的主体也是 DSP（§2.2）；
2. "智能识别场景"只有语义模型能满足，YAMNet 是唯一同时满足 小/准/许可证干净/有现成 ONNX 的模型（§3.3）；
3. 学术线两篇 CHI 论文（2023 selective multimodal、2025 semantic LSTM）的结构均为"分类 + 映射 + 渲染"，混合架构与之同构；
4. Rust 生态零障碍且全部活跃维护：`wasapi` 0.27.0（含按进程录制）、`ort` 2.0.0-rc.15（静态链接免 DLL）、`rustfft` 6.4.1；**无 Python、无 libtorch、无 GPL**（§4）；
5. 分发友好：唯一新文件是 yamnet.onnx（≈15MB），可内嵌或首启下载（§6 路线 B）。

**实施顺序建议**：先落地路线 A（一至两天可出效果、立刻可用），再接 YAMNet 语义层做门控与场景预设；两者解耦，语义层故障时快通道自动独立工作（降级即路线 A）。

**需要实测的两个点**（本调研无法代验）：
- [audiomagic/yamnet-onnx](https://huggingface.co/audiomagic/yamnet-onnx/blob/main/README.md) 在 `ort` 2.0.0-rc.15 下加载与速度；
- WASAPI loopback 在目标机器的 period 与音效同步表现（参考 [Microsoft Q&A 关于 loopback 不连续的帖子](https://learn.microsoft.com/en-us/answers/questions/1188388/persistent-audio-discontinuity-in-wasapi-loopback)）。

## 8. 项目接入点分析（宿主 DfoVibration 实测源码得出, 2026-11-08）

> 本章为宿主架构核对结论（源码: `src/vibration/{mod,core}.rs` / `src/xinput.rs` / `CONTEXT.md`），
> 把 §7 的推荐管线落到本项目上。

### 8.1 现有震动链路（audio 模式必须汇入的既有管道）

```
注入DLL → 共享内存 ring (VibEvent 16B: etype/strength/tick) → vibration_thread::run()
  → RouteEngine(S1/S4).push_event → tick(60槽参数) → send_vibration(L,R) → XInputSetState
```

关键事实:
- **全项目唯一的马达出口** = `vibration/core.rs::send_vibration`（扫描 0..4 槽找已连接手柄），
  且带 v24.41 的"最后写方记账"写入去重（`LAST_XINPUT_WRITE` 打包 slot+L+R）。
- **60 槽参数** = 引擎全部强度治理的输入（master×上限/衰减/合并），由 `vibration/params.rs`
  双向映射到 `Vibration.toml`（路线隔离 S1/S4 各一份）。
- 事件号 `VEV_*` 在 `vibration/core.rs`；`VibEvent.etype: u32` 有扩展空间。

### 8.2 接入方案: mpsc 合流进 vibration_thread（唯一正确姿势）

**禁止**开独立线程直接调 `send_vibration` —— 会与震动线程互相覆盖输出、绕过写入去重
记账（两个写方都自以为"最后写方"），还会绕开 60 槽强度治理（音频可能瞬间拉满马达）。

正确形态（零改动输出侧，全部既有治理自动生效）:

```
[新增] audio_haptics 线程
  wasapi loopback (10ms period) → 环形缓冲
    ├─ 快通道 DSP: rustfft 谱通量 onset + 频带能量 → (延迟 20-40ms)
    └─ 慢通道 SED: ort+yamnet → 场景/门控 (0.5-1s)
  → mpsc::sync_channel::<AudioHapEvent>(容量 64)
      ↓
vibration_thread::run() 主循环 (在 poll SHM ring 的同一轮里 try_recv 非阻塞合流)
  → engine.push_event(&VibEvent { etype: VEV_AUDIO_*, strength, tick })   ← 新增事件号
  → 既有 tick/合成/衰减/上限不变 → send_vibration 唯一出口
```

要点:
1. **新事件号 `VEV_AUDIO_*`**（如 AUDIO_ONSET_LOW/AUDIO_ONSET_HIGH/AUDIO_AMBIENT）走
   `VibEvent.etype` 现有 u32 空间——**不改共享内存布局**（`VibShm` 262208 字节断言不动，
   音频事件不走 SHM，无 DLL 侧改动）。
2. **60 槽参数语义**: 音频项新增专属槽位需要动 `params.rs` 宏表 + `VibrationConfig`
   （冻结契约，走 cookbook 配方 1 的六步）。**Phase 0 可先不动契约**——把音频事件映射到
   现有槽位（onset→attack 槽族、低频能量→hit 槽族）做灰度验证，参数面板复用现有 UI。
3. **暂停/白名单语义**: 音频引擎须尊重 `AppState::is_paused()` 与前台进程白名单——
   飞智的"只读指定进程音频"对应本项目白名单的天然映射（游戏不在白名单 → 音频引擎闲置）。
   `wasapi` crate 的 `record_application`（按 PID 录制）是精确对齐手段（§4.2）。
4. **WASAPI 环回的平台特性**（§4.2 gotcha）: 输出设备**无声音播放时不推进**——游戏场景
   必然持续出声所以无碍；但需要在引擎里处理"ring 长时间无数据"的静默检测（自动降级/恢复）。
5. **GUI**: 新页面 `gui/audio_page/`（cookbook 配方 2: Page 枚举 + TABS + Rail 图标），
   复用 `vibration_page` 的滑块体系；实时电平/频谱可视化用 egui 直方图（不引第三方绘图）。

### 8.4 风险清单（实施前必读）

1. **`ort` 2.0.0-rc.15 是 RC**：构建期静态链接下载二进制依赖网络（CI 需缓存）；
   yamnet-onnx 的图兼容性需在真实 ort 版本上实测（报告 §6 路线 B 已列）。
2. **AudioSet 权重灰区**：YAMNet 官方权重 Apache-2.0 干净；PANNs/EfficientAT 权重是
   "研究用途"灰区——商用/分发前只走 YAMNet 官方权重。
3. **GPL 红线**: aubio/essentia 全家禁用（连 dev-dependency 都不要引入）。
4. **延迟目标**: P0 的 20-40ms 达标路径已被 xbox-audio-rumble-studio（同链路 Python 实现）
   和 DS5Dongle fork（游戏声→DualSense）双料验证；P1 的 0.5-1s 语义窗只用于门控/场景，
   **不承担瞬态触发**——两条通道的职责必须在映射表里写死，否则会被误当成"AI 识别慢"。
5. **DNF 场景的特殊性**: DFO 音效密度极高（多技能同屏），快通道需要 per-帧节流与
   强度上限（既有 60 槽治理覆盖）；BGM 门控在 P1 之前靠"频带 + onset 阈值"近似。
